# 개미수열 (Look-and-Say Sequence) — 가운데 두 자리 구하기

## 문제

양의 정수 `n` (3 < n < 100)이 주어질 때, 개미수열의 `n`번째 항 `Ln`의 자릿수 중 가운데 두 자리 수(`m`)를 출력하는 함수를 작성한다.

개미수열은 이전 항을 "몇 개의 몇" 형태로 읽어서 다음 항을 만드는 수열이다.

```
L1 = 1
L2 = 11        (1이 1개)
L3 = 21        (1이 2개)
L4 = 1211      (2가 1개, 1이 1개)
L5 = 111221    (1이 1개, 2가 2개, 1이 1개)
...
```

**예시**

- 입력 `n=5` → `L5=111221` → 출력 `m=12`
- 입력 `n=8` → `L8=1113213211` → 출력 `m=21`

`n≥2`부터 `Ln`의 길이는 항상 짝수이므로, 길이의 정중앙(`mid = 길이/2`)을 기준으로 바로 앞뒤 한 글자씩(`mid-1`, `mid` 위치)을 이어붙이면 가운데 두 자리를 구할 수 있다.

## 프로젝트 구조

```
src/
  solution1.ts   # 풀이 1 — 문자열 기반
  solution2.ts   # 풀이 2 — 배열(Run-Length Encoding) 기반
  solution3.ts   # 풀이 3 — 정규식 기반
  cli.ts         # 터미널에서 세 풀이를 직접 실행해볼 수 있는 CLI
test/
  solution1.test.ts
  solution2.test.ts
  solution3.test.ts
```

## 실행 방법

```bash
npm install
npm test              # 세 풀이의 테스트(총 18개) 실행
npm run solve -- <n>  # n을 넣어 세 풀이의 결과를 직접 확인
```

```bash
$ npm run solve -- 5
n = 5
풀이1 (문자열 기반): 12
풀이2 (배열/RLE 기반): 12
풀이3 (정규식 기반): 12
```

## 풀이 1 — 문자열 기반 (`src/solution1.ts`)

`L1="1"`에서 시작해서 문자열을 그대로 순회하며 연속된 같은 숫자를 세어 `(개수)(숫자)` 형태의 새 문자열로 바꾸는 과정(`nextTerm`)을 `n-1`번 반복해 `Ln`을 만든다.
완성된 문자열의 길이를 구해 중앙 인덱스를 계산하고, `slice`로 가운데 두 글자를 잘라낸다.

가장 직관적인 구현이지만, 매 단계마다 전체 문자열을 새로 만들기 때문에 항의 길이가 길어질수록 메모리와 시간 비용이 그대로 늘어난다.

**시간/공간 복잡도**: `L`을 `Ln`의 자릿수 길이라 하면,

- `nextTerm` 한 번 호출은 문자열을 한 번 순회하므로 `O(현재 항 길이)`
- `nthTerm`은 이걸 `n-1`번 반복하는데, 항 길이가 매 단계 약 1.303배씩(Conway's constant) 기하급수적으로 늘어나기 때문에 전체 합은 등비수열 합 공식에 의해 마지막 항 길이에 수렴한다 → 시간 복잡도 **O(L)**
- 마지막 항 문자열 하나만 들고 있으면 되므로 공간 복잡도도 **O(L)**

## 풀이 2 — 배열/RLE 기반 (`src/solution2.ts`)

항을 문자열이 아니라 `{ digit, count }` 쌍의 배열로 표현한다. 개미수열을 만드는 규칙 자체가 "숫자가 몇 번 반복되는지 읽는" 것이므로, 이미 이 형태로 관리하고 있으면 각 쌍을 "count, digit" 순서로 풀어 이어붙이기만 하면 다음 항이 나온다(`nextRuns`).

가운데 두 자리를 구할 때도 전체를 문자열로 합치지 않고, `digitAt` 함수로 원하는 위치(인덱스) 하나만 조회한다 — 각 구간(run)이 차지하는 범위를 커서로 추적하다가 찾는 인덱스가 그 범위 안에 들어오면 해당 숫자를 바로 반환하는 방식이다.

풀이 1과 결과가 항상 같은지 `n=4~45` 범위에서 직접 교차 검증했다.

**시간/공간 복잡도**: run(구간)의 개수를 `R`이라 하면 (각 run은 최대 3개까지만 반복되므로 `R`도 항 길이 `L`과 같은 비율로, 즉 `O(L)`로 늘어난다),

- `nextRuns` 한 번 호출은 run 배열을 한 번 순회하므로 `O(현재 run 개수)`
- `nthRuns`도 이를 `n-1`번 반복하고, run 개수 역시 기하급수적으로 증가하므로 전체 합은 마지막 항의 run 개수에 수렴 → 시간 복잡도 **O(R) = O(L)**
- `digitAt`은 목표 인덱스를 찾을 때까지 run을 순회하므로 최악의 경우 **O(R)**, 가운데 두 자리를 구하려고 두 번 호출해도 여전히 **O(R)**
- 공간 복잡도는 마지막 항의 run 배열 크기만큼이므로 **O(R) = O(L)**

즉 풀이 2는 문자열 대신 압축된 배열을 쓰지만, run 개수 자체가 항 길이에 비례해서 늘어나기 때문에 **점근적 복잡도는 풀이 1과 동일한 O(L)** 이다 — 상수 배(문자열 concat 비용 vs 배열 push 비용) 차이만 있을 뿐, 계산량의 차수 자체를 줄이지는 못한다.

## 풀이 3 — 정규식 기반 (`src/solution3.ts`)

풀이 1과 같은 문자열 기반이지만, 연속된 같은 숫자 구간을 직접 포인터로 찾는 대신 정규식으로 찾는다. `term.replace(/(\d)\1*/g, ...)`에서 `(\d)`가 숫자 하나를 캡처하고 `\1*`가 "바로 앞에서 캡처한 숫자와 같은 숫자가 0번 이상 반복"을 의미하므로, 연속된 같은 숫자 구간 전체가 한 번의 매치로 잡힌다. 매치된 문자열의 길이(개수)와 캡처된 숫자를 이어붙여 치환하면 다음 항이 만들어진다(`nextTerm`). 이후 흐름(`nthTerm`, 가운데 두 자리 추출)은 풀이 1과 동일하다.

풀이 1과 결과가 항상 같은지 `n=4~45` 범위에서 직접 교차 검증했다.

**시간/공간 복잡도**: 정규식 엔진이 내부적으로 문자열을 한 번 순회하며 매치를 찾는 것이므로, 풀이 1의 수동 포인터 순회와 점근적으로 동일하다 → 시간 복잡도 **O(L)**, 공간 복잡도 **O(L)**.
코드는 더 간결하지만 복잡도상의 이득은 없다.

## 소감

세 풀이 모두 처음엔 무리 없이 동작했지만, 검증 과정에서 중요한 사실을 발견했다.
개미수열의 길이는 **지수적 증가**를 보인다. 이 때문에 `n`이 99에 가까워지면 `L99`의 자릿수는 대략 2천억 자리에 달해서, 문자열이든 배열이든 어떤 방식으로 표현하더라도 그 항 자체를 실제로 만들어내는 것 자체가 현실적으로 불가능해진다.

처음엔 "풀이 2(배열 기반)가 풀이 1보다 훨씬 빠르고 큰 `n`도 처리할 수 있을 것"이라 기대했지만, 실제로는 세 방식 모두 같은 지수적 한계에 부딪힌다는 걸 확인했다.
런렝스 인코딩이 압축해주는 건 "각 구간을 숫자 두 개(digit, count)로 표현하는 것"뿐이고, 구간(run)의 **개수** 자체는 여전히 항 길이에 비례해서 지수적으로 늘어나기 때문이다.
풀이 3(정규식 기반)도 겉보기엔 코드가 가장 간결하지만, 결국 정규식 엔진이 내부적으로 문자열을 순회하는 것이라 풀이 1과 다를 바 없었다.
즉 표현 방식이나 문법을 바꾼다고 해서 "가운데 두 자리만 구해도 항 전체를 생성해야 한다"는 문제의 근본적인 특성 자체는 피할 수 없었다.

세 풀이를 나란히 만들고 실제 값으로 교차 검증까지 해보면서, 겉보기에 다른 접근들이 실제로는 같은 한계를 공유한다는 걸 코드로 직접 확인해볼 수 있었던 게 이번 문제를 풀며 가장 흥미로웠던 부분이다.
